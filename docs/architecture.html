FlowGuard: an intrusion detector that admits what it doesn't know

A network intrusion detection system built on flow features. It classifies known attacks, flags unfamiliar traffic as a possible zero-day, explains every alert, and gets tested on a second dataset and against an attacker who tries to slip past it.

Why this oneIt is clearly a security project and the data is public and safe. A week with AI-assisted coding is enough to finish it properly.
What lifts it above a Kaggle notebookCross-dataset testing, zero-day simulation, adversarial evasion and per-alert explanations. Most student IDS projects stop at "99% accuracy".
What you demoUpload a pcap. The dashboard lists the flows it flagged and gives the reason for each one.
The questions the project answers

Four research questions

Every experiment exists to answer one of these. Put them in your introduction and answer them in your conclusion.

RQ1How well do linear, tree and neural models detect and classify attacks on data from the same network they were trained on?
RQ2How much of that performance survives when the model is moved to a different network (train on CIC-IDS2017, test on CSE-CIC-IDS2018)?
RQ3Can a hybrid design (anomaly detector plus classifier) catch an attack family it has never seen during training?
RQ4How easily can an attacker who only controls their own traffic evade the detector, and how much does adversarial training help?

The offline pipeline is where you do the research and produce the report. The online pipeline is the working detector you demo. They use the same saved preprocessing, so the model sees live traffic exactly the way it saw training data.

Components

What each box does

1 · Datasets

src/flowguard/data/load.py

Both datasets come from the Canadian Institute for Cybersecurity and were made with the same flow tool (CICFlowMeter). That shared feature set is what makes the cross-dataset test possible.

DatasetRoleNotes
CIC-IDS2017Training and in-dataset testingAbout 2.8M flows over 5 days. Use the corrected release (Engelen et al., 2021). The original has mislabeled flows and broken features.
CSE-CIC-IDS2018Cross-dataset test onlyAbout 16M flows on a different network. Use a corrected release if you can get one. Take a stratified sample of 1–2M flows so it fits in RAM.
Your own pcapDemo onlyA short capture of you running nmap and hydra against a VM you own, plus normal browsing. Never scan hosts you don't own.

2 · Clean and harmonize

clean.py · labels.py · split.py
  • Drop identifiers the model must not learn from: Flow ID, Src IP, Dst IP, Src Port, Timestamp. If you keep them, the model memorizes the lab's attacker IP and your results are fake.
  • Replace inf values (they show up in Flow Bytes/s and Flow Packets/s) with NaN, then impute. Remove exact duplicate rows before splitting, so the same flow can't end up in both train and test.
  • Map column names between the two datasets, since the releases spell some features differently. Keep only the columns they share.
  • Map the fine-grained labels to one shared set of families: Benign, DoS, DDoS, PortScan, BruteForce, WebAttack, Botnet, Infiltration.
  • Save everything as Parquet. It loads much faster than CSV and keeps the dtypes.

3 · Feature pipeline

features/pipeline.py

One scikit-learn Pipeline: median imputation, then QuantileTransformer or StandardScaler (flow features are very heavy-tailed, so try a log1p first), then optional feature selection that drops near-constant and highly correlated columns. Fit it on the training split only and save it with joblib. The online service loads this same file.

The hybrid detector combines the best classifier with the anomaly model. This is the design choice that answers RQ3:

score = classifier.predict_proba(flow) anom = anomaly_model.score(flow) if max(score[attacks]) ≥ τ → ALERT: known attack (family = argmax) elif anom ≥ θ → ALERT: unknown anomaly (possible zero-day) else → benign τ, θ tuned on validation to keep benign false positives ≤ 1 per 1,000 flows

5 · Evaluation harness

eval/protocols.py · metrics.py

One function per protocol, each of which logs to MLflow. Every model goes through every protocol, so the results table fills itself in.

ProtocolTrain onTest onAnswers
P1 · In-datasetFirst 70% of each day of 2017, by timeLast 30% of each dayRQ1
P2 · Cross-datasetAll of 20172018 sample, shared families onlyRQ2
P3 · Leave-one-family-out2017 minus one attack familyThe held-out family plus benignRQ3
P4 · AdversarialP1 model, then the hardened modelPerturbed attack flowsRQ4

Metrics: macro-F1 and per-class recall (accuracy is meaningless when about 80% of flows are benign), benign false-positive rate expressed as alerts per 10,000 flows, PR-AUC, confusion matrix, and throughput in flows per second. For P3, report the share of the held-out family flagged as unknown anomaly. For P4, report the evasion rate.

6 · Adversarial lab

adversarial/threat_model.py · attacks.py · defenses.py

Threat model: the attacker controls their own packets but not the server's replies, and must keep the attack working. In practice they can pad packets, add delays between packets, and send extra dummy packets. They can't shrink the payload or change backward-direction features.

  • Mutable-feature mask: list which of the ~80 features the attacker can change and in which direction (most can only increase). This mask is the core of the security argument.
  • Attacks: masked PGD on the MLP (white-box). Transfer those samples to XGBoost, and also run a black-box attack on it (HopSkipJump from IBM ART, or a simple masked random search). Clip to realistic bounds and recompute dependent features such as means and rates.
  • Defenses: adversarial training (add perturbed samples to training) and a model restricted to features the attacker can't change. Compare evasion rate against clean macro-F1. That trade-off curve is one of your key figures.

7 · Explainability

explain/shap_explain.py

shap.TreeExplainer on XGBoost. Globally, show a beeswarm plot per attack family. Do these features make networking sense? A PortScan driven by tiny flow duration and few packets does. A model driven by Dst Port alone is a warning sign. Locally, the top 5 features with their values become the reason text attached to each alert in the dashboard.

8 · Online detection service

serve/ · app/dashboard.py
  • Flow extractor: the Python cicflowmeter package turns a pcap into flow rows. Its feature names differ a little from the Java tool used for the datasets, so map them with the same column map as step 2.
  • FastAPI: POST /predict takes flow rows and returns label, confidence, anomaly score and top features. POST /pcap runs the full chain.
  • Streamlit dashboard: upload a pcap and get an alert table (time, src→dst, family or "unknown", confidence), an attack mix chart, and a SHAP waterfall when you click an alert.
  • Be honest in the report: live traffic from your own machine differs from the lab datasets, so treat the demo as a qualitative showcase and keep the quantitative claims to P1–P4.

Traps

Mistakes that quietly ruin IDS results

Identifier leakageIPs, ports and timestamps let the model recognize the lab instead of the attack. Drop them, then check SHAP to confirm nothing similar sneaks in.
Duplicates across splitsDoS and scan traffic produce many identical flows. Deduplicate before splitting, or test scores get inflated.
Scaler fit on all dataFit the pipeline on train only. The test set has to stay unseen in every way.
Reporting accuracyA model that says "benign" every time gets about 80%. Lead with macro-F1 and false-positive rate.
Tiny classesInfiltration and Heartbleed have very few samples. Merge or drop them, and say so. Don't report 100% recall on 11 samples.
Unrealistic attacksAn adversarial example that changes a feature the attacker can't control proves nothing. The mask is what makes P4 credible.
